## 1. Vị trí trong kiến trúc

```
Nguồn (POS, kho, CRM, app mức 2, connector, MCP, nhập lô)
        │  POST /documents · /documents/batch · /documents/submit
        ▼
┌─────────────────────────── Cửa nạp Kernel (không đổi luật) ───────────────────────────┐
│ khuôn (zod) → tổng tiền → chủ chứng từ → postDocumentIn → định khoản → sổ              │
│        │ từ chối (400 / 409)                                                           │
│        ▼                                                                               │
│  modules/intake (MỚI)                                                                  │
│   preflight(doc) — gom L1…L4 (+ L5 khi bấm Kiểm thử)  ──►  intake_inbox (bể chờ)       │
│   phản hồi giữ mã lỗi + meta.intake + error.details.findings                           │
└────────────────────────────────────────────────────────────────────────────────────────┘
        │ đạt khuôn                                   ▲ nộp lại (đúng cửa nạp)
        ▼                                             │
accounting_events (pending / posted / error) ──► Trạm kiểm tra đầu vào (web) ◄── bể chờ
```

- `modules/intake` nằm trong `packages/kernel` (gần cửa nạp, cần gọi hàm Kernel), **không** ghi `ledger_*`, `accounting_events`. Lớp: `K kernel/intake`.
- Đường hợp lệ **không** chạy tiền kiểm đủ lớp: chỉ khi cửa nạp đã từ chối, hoặc người dùng bấm Kiểm thử. Chi phí đường thường không đổi.

## 2. Dữ liệu

```sql
CREATE TABLE intake_inbox (
  id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  tenant_id       bigint      NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  received_at     timestamptz NOT NULL DEFAULT now(),
  last_seen_at    timestamptz NOT NULL DEFAULT now(),
  channel         text        NOT NULL CHECK (channel IN ('api','batch','submit','app','connector','mcp','trial')),
  source_system   text,                      -- từ nguyên văn nếu đọc được
  actor           text        NOT NULL,      -- user:<id> | apikey:<id>
  app_key         text,                      -- khoá app (ADR-0011 mức 2) nếu có
  doc_key         text,                      -- có thể trống khi khuôn hỏng
  doc_type        text,
  version         integer,
  payload_raw     jsonb       NOT NULL,      -- KHÔNG sửa (R-INTAKE-7); quá giới hạn → {"truncated":true}
  payload_hash    text        NOT NULL,      -- sha256 của nguyên văn chuẩn hoá
  payload_bytes   integer     NOT NULL,
  patches         jsonb       NOT NULL DEFAULT '[]',   -- [{at, by, reason, ops:[RFC 6902]}], chỉ thêm
  findings        jsonb       NOT NULL,      -- danh sách phát hiện lần gần nhất
  score           smallint    NOT NULL CHECK (score BETWEEN 0 AND 100),
  attempt_no      integer     NOT NULL DEFAULT 1,
  status          text        NOT NULL DEFAULT 'open'
                  CHECK (status IN ('open','trial','resubmitted','fixed_at_source','accepted','dismissed')),
  event_id        bigint REFERENCES accounting_events(id),  -- khi đã thành sự việc
  accepted_codes  text[]      NOT NULL DEFAULT '{}',        -- mã warn đã chấp nhận
  resolved_by     text,
  resolved_at     timestamptz,
  resolution_note text
);
CREATE UNIQUE INDEX intake_inbox_open_dedupe ON intake_inbox (tenant_id, payload_hash) WHERE status IN ('open','trial');
CREATE INDEX intake_inbox_doc_idx    ON intake_inbox (tenant_id, doc_key) WHERE status = 'open';
CREATE INDEX intake_inbox_status_idx ON intake_inbox (tenant_id, status, received_at DESC);
-- RLS như 0041; COMMENT ON mọi cột; ketoan_app: SELECT, INSERT, UPDATE, DELETE (DELETE chỉ cho dọn theo hạn giữ)
```

- Gửi lại **cùng nguyên văn** khi mục còn mở → `attempt_no + 1`, `last_seen_at`, không thêm dòng.
- Giới hạn nguyên văn: 256 KB. Lớn hơn → lưu `{"truncated": true, "head": …}` + băm + kích thước; vẫn có phát hiện L1.
- `DELETE` là ngoại lệ có chủ đích: bể không phải sự thật kế toán (ADR-0014 D10). Chỉ job dọn theo hạn giữ xoá; route không có `DELETE`.
- Không bảng nào của Kernel đổi. `accounting_events` chỉ nhận thêm `extra.intake` trong `payload` của sự việc sinh từ sửa tại bể (dấu lệch nguồn, qua khuôn có sẵn `extra`).

## 3. Danh mục mã `IN-*` (`bizcity_intake_findings@1`)

Tệp nguồn: `packages/contracts/src/intake-findings.ts` (một dòng một mã, như `ERROR_CATALOG`), bảng người đọc: `docs/contracts/BIZCITY-INTAKE-FINDINGS-v1.md`, trang bài học: `docs/huong-dan/loi-dau-vao/<mã>.md`. Check `SC-INTAKE-1`: ba nơi khớp nhau.

```ts
interface IntakeCodeSpec {
  layer: 'L1' | 'L2' | 'L3' | 'L4' | 'L5';
  severity: 'block' | 'warn' | 'hint';   // block chỉ khi Kernel cũng chặn (D021-2, D021-3)
  weight: number;                        // điểm trừ khi warn (0–100)
  title: string;                         // một dòng, tiếng Việt
  why: string;                           // vì sao kế toán cần — viết cho thực tập sinh
  fix: string;                           // sửa ở nguồn thế nào
  ref: string;                           // R-*, hợp đồng, căn cứ
  acceptable: boolean;                   // warn: kế toán trưởng cho phép chấp nhận không
}
```

Danh mục **nháp** cho W1. Mức có dấu ⚑ phải xác minh với Kernel ở W1 (10-HIEN-TRANG §3); không xác minh được thì để `warn`.

## 4. Bộ tiền kiểm

```ts
// packages/kernel/src/modules/intake/preflight.ts
preflight(trx, auth, raw: unknown, opts: { layers?: ('L1'|'L2'|'L3'|'L4'|'L5')[] }): Promise<{
  findings: Finding[];            // đã sắp: block → warn → hint, theo lớp
  score: number;
  parsed?: IngestDocument;        // có khi L1 đạt
  entries?: DraftEntry[];         // có khi L5 chạy và đạt
}>
```

- **L1** `ingestDocumentSchema.safeParse` → mỗi `issue` của zod ánh xạ sang mã `IN-SHAPE-*` theo `issue.code`, `path` chuyển dạng `lines[2].qty`. Không đưa `issue.message` của zod cho người dùng.
- **L2** tách `assertTotals` thành `totalsProblems(doc): Problem[]`; cửa nạp gọi `totalsProblems` rồi ném phần tử đầu — **một** chỗ luật (D021-2). L1 hỏng một phần thì L2 chạy trên phần đọc được (vd tổng vẫn so được khi một dòng thiếu `name`).
- **L3, L4** gọi đúng các hàm tra cứu Kernel đang dùng, ở chế độ "trả lỗi" thay vì "ném". Hàm nào Kernel đang ném thì thêm biến thể trả danh sách, cửa nạp dùng biến thể đó (không viết lại luật).
- **L5** chỉ khi L1–L4 không còn `block`: mở giao dịch, `SET LOCAL statement_timeout = '3s'`, chạy `postDocumentIn` với `{ post: true, force: true }` như `preview()` (R-EVENT-11), lấy bút toán, **ROLLBACK**. Không phát sự kiện (outbox nằm trong giao dịch bị huỷ).
- **Điểm:** có `block` → 0; không thì `100 − Σ weight(warn chưa chấp nhận)`, sàn 0; `hint` không trừ.

## 5. API

| Lời gọi | Quyền | Việc |
|---|---|---|
| (lỗi của) `POST /documents`, `/documents/batch`, `/documents/submit` | như cũ | mã HTTP cũ; `error.details.findings`; `meta.intake = { id, score, url }` (lô: từng dòng có `intakeId`) |
| `POST /api/v1/intake/preflight` | `documents:write` | Kiểm thử: `{ document, save?: boolean }` → `{ findings, score, entries? }`; `save` → mục `trial` |
| `GET /api/v1/intake` | `documents:read` | lọc `status`, `channel`, `source`, `docType`, `actor`, `code`, `from`, `to`; phân trang |
| `GET /api/v1/intake/:id` | `documents:read` | nguyên văn, bản vá, phát hiện từng lần, lịch sử |
| `POST /api/v1/intake/:id/patch` | `documents:write` (mục của mình) / `documents:edit-all` | `{ ops, reason }` → chạy lại tiền kiểm, trả phát hiện mới + so sánh với lần trước |
| `POST /api/v1/intake/:id/resubmit` | như trên | nguyên văn + bản vá → **đúng** cửa nạp (`submitDocumentIn`); đạt → `resubmitted`, `event_id` |
| `POST /api/v1/intake/:id/accept` | vai trò được phép (cấu hình) | `{ codes, reason }` — chỉ mã `warn` có `acceptable`; ghi bằng chứng |
| `POST /api/v1/intake/:id/dismiss` | `documents:edit-all` | `{ reason }` |
| `GET /api/v1/intake/score` | `documents:write` (mọi kế toán, Q3) | `groupBy = source | actor | docType | code | week`, `from`, `to` |

Action đọc cho AI (W5): `core.intake.list`, `core.intake.get`, `core.intake.explain` — `effect: 'read'`, `expose.ai: 'read'`. Không có action ghi nào phơi cho AI.

## 6. Vòng đời

```
                ┌────────── nguồn gửi lại cùng docKey, đạt ──────────► fixed_at_source
                │
cửa nạp từ chối ─► open ──► patch (lặp) ──► resubmit đạt ──────────────► resubmitted
                │                     └─► còn warn ─► accept (có lý do) ─► accepted
                └────────── kế toán trưởng bỏ (có lý do) ───────────────► dismissed
Kiểm thử (save) ─► trial ──► (7 ngày) xoá
open / đóng ─► (đóng + 90 ngày) xoá
```

- Tự đóng (`fixed_at_source`): trong giao dịch cửa nạp nhận sự việc thành công, Kernel gọi `intake.closeBySource(trx, tenantId, docKey, eventId)`. Đăng ký kiểu hook như `registerIncomingPreparer` để Platform không import Kernel.
- `resubmitted` / `accepted`: sự việc mang `extra.intake = { inboxId, patched, acceptedCodes }` → ACC14 / sổ chi tiết hiện dấu "sửa tại bể" (lệch nguồn).

## 7. Màn hình (web)

**Trạm kiểm tra đầu vào** (thay ACC14 tại `/chung-tu`, giữ mã ACC14):

| Thẻ | Nguồn | Mặc định sắp |
|---|---|---|
| **Cần sửa** | bể chờ `open` | điểm tăng dần, mới nhất |
| Chờ định khoản | `accounting_events.pending` (như hôm nay) | — |
| Lỗi định khoản | `accounting_events.error` (như hôm nay) | — |
| Đã xử lý | bể chờ đã đóng (7 ngày gần nhất) | — |
| Thử của tôi | bể chờ `trial` của người đang xem | — |

Khung chi tiết một mục bể:

1. **Câu kết luận trước**: "Chứng từ HD-0012 chưa vào sổ: 2 lỗi phải sửa, 1 cảnh báo. Điểm 0/100." + mã tra cứu (sang Bàn điều tra khi là sự cố hệ thống).
2. **Lỗi theo lớp** (Khuôn · Số học · Danh mục · Nghiệp vụ · Định khoản): mỗi lỗi một thẻ — tiêu đề, trường (bấm → nhảy tới ô), đã gửi ↔ đúng phải là, **Vì sao**, **Sửa ở nguồn**, nút **Bài học**.
3. **Chứng từ**: dạng form theo `docType` (ô lỗi viền đỏ, ô cảnh báo viền vàng) hoặc JSON; sửa → thành bản vá, bắt buộc lý do.
4. **Nút**: Kiểm thử · Nộp lại · Chấp nhận cảnh báo (nếu được phép) · Bỏ (kế toán trưởng).
5. **Lịch sử lần thử** (A/B): mỗi lần một dòng — lúc, ai, điểm, lỗi hết / lỗi mới; chọn hai lần để so.

**Bảng điểm đầu vào** (mới, nhóm Kế toán, mọi kế toán xem — Q3):

- Ô số: tỷ lệ đạt lần đầu (7 / 30 ngày), điểm trung bình, mục mở, mục mở lâu nhất, số lần sửa tại bể.
- Bảng: theo nguồn, theo người lập, theo loại chứng từ (cột: số gửi, đạt lần đầu, điểm TB, mã lỗi hay gặp nhất).
- Mười mã lỗi nhiều nhất (bấm → danh sách mục + bài học).
- Xu hướng theo tuần.
- Câu dẫn cố định: "Bảng này để cùng học cách nhập đúng, không để đánh giá cá nhân."

Bản mẫu tĩnh: `mockups/tram-kiem-tra.html` (S021-3).

## 8. Chấm điểm và chỉ số

| Chỉ số | Công thức |
|---|---|
| Điểm mục | §4 |
| Tỷ lệ đạt lần đầu | số `docKey` vào sự việc mà **chưa từng** có mục bể ÷ số `docKey` khác nhau nhận được (cả hai trong khung thời gian) |
| Thời gian xử lý | `resolved_at − received_at` (trung vị) |
| Tỷ lệ sửa tại bể | `resubmitted + accepted` ÷ mục đã đóng |
| `DG-INTAKE-1` | mục `open` quá ngưỡng (mặc định 3 ngày, `bizcity.intake.open_alert_days`) → cảnh báo |

## 9. Sự kiện

| Loại | Khi | `data` (chỉ mã và số — R-INTAKE-12) |
|---|---|---|
| `bizcity.intake.rejected` | tạo mục `open` (không phát cho lần gửi trùng) | `{ inboxId, docKey?, docType?, channel, codes[], score }` |
| `bizcity.intake.resolved` | mục đóng | `{ inboxId, docKey?, status, eventId?, patched }` |

App ngoài tiến trình nhận qua webhook (PR-2b) nếu đăng ký; nguồn biết chứng từ nào cần sửa ở phía mình.

## 10. Bảo mật, dữ liệu cá nhân

- RLS như mọi bảng có `tenant_id`; người lập (không `documents:edit-all`) chỉ sửa / nộp lại mục có `actor` của mình.
- Nguyên văn, bản vá **không** vào log, span, sự kiện, webhook, MCP (`core.intake.get` cho AI trả phát hiện, không trả nguyên văn).
- Hạn giữ 90 / 7 ngày (Q2); xoá thật.
- Khoá app: mục bể ghi `app_key`; app đọc được mục của chính nó qua `GET /intake?app=me` (sau cổng route app — chỉ GET).
